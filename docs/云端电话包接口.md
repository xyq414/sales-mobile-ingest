# 云端电话接口：legacy recording package v1 + call-fact v1

## 目的与边界

云端消费者不需要理解 OPPO、MTP、SyncTech XML、Windows state 或本机绝对路径。现有 recording-backed 三文件 v1 保持原定义；无录音电话使用独立的 call-fact v1 流，绝不把旧三文件 readiness gate 改成可选文件。

## Call-first versioned route

```text
<cloud_handoff_root>/
  _phone-call-facts-v1/<call_id>.json
  _call-recording-links-v1/<link_id>.json
  <legacy salesperson/date/call directories...>
```

- `_phone-call-facts-v1` 中每个 JSON 原样符合 `phone-call/v1`；missed、rejected 或普通无录音电话不要求 audio。
- `_call-recording-links-v1` 符合 `call-recording-link/v1`，用 `recording_id` 将 PhoneCall 与旧 recording/event v1 关联。NO_MATCH/AMBIGUOUS 后续可在同一 `link_id` 原子更新，不产生第二个电话事实。
- call fact 以 `call_id` 幂等；合法 enrichment 更新同一 JSON。旧三文件包仍为 immutable snapshot，不受新流更新影响。
- `publish-call-facts --once` 可独立发布；`watch/ingest --once` 也会尝试发布。写入本机 sync root 不等于网络或远端消费完成。

手机采集仍写入本机 `data_root`；只有完成校验的三文件电话包才会进入单独配置的 `cloud_handoff_root`。坚果云 Windows 客户端只负责同步该目录，项目不调用坚果云 API、WebDAV 或登录流程。

## 目录与三文件规范

```text
<cloud_handoff_root>/
  <salesperson_id>_<sanitized_salesperson_name>/
    YYYY-MM-DD/
      YYYYMMDD_HHMMSS_<event_id-short>/
        audio.<original-extension>
        recording.json
        event.json
```

- 销售目录的业务唯一身份是 `event.json.salesperson_id`；目录名仅用于浏览。Windows 非法字符会确定性替换，首次成功发布后同一 `salesperson_id` 的历史目录名固定，因此改名不会制造第二份电话包。
- 日期与时间来自最终 `event.json.occurred_at` 自带时区的日历值，不使用导入或同步日期。
- 电话目录由时间和 `event_id` 的短码组成；不包含电话号码或联系人，同一秒多通电话也不会碰撞。
- 每个电话目录必须**恰好**有三份普通文件。任何 `READY`、manifest、XML、日志、state、临时文件、转写或其他第四个文件都会使包无效。

## 文件语义

| 文件 | 规则 |
| --- | --- |
| `audio.<ext>` | 原始录音字节的副本，不转码、不改 tag；SHA-256 必须同时匹配两份 JSON。 |
| `recording.json` | `cloud-recording-package/v1`，保留技术、时间、设备、时长、hash 与采集 provenance；不携带本机源文件名、源相对路径或号码。 |
| `event.json` | `cloud-communication-event-package/v1`，保留 `event_id`、`recording_id`、销售、通话时间、号码（如可靠）、方向、时长、provenance 与媒体 hash。`media_ref` 固定为当前目录内的 `audio.<ext>`。 |

对应机器 schema：

- `contract/cloud_recording_package.schema.json`
- `contract/cloud_communication_event_package.schema.json`

仅含虚假信息的样例见 `contract/examples/cloud_recording_package.example.json` 与 `contract/examples/cloud_communication_event_package.example.json`。

两个 JSON 都不含开发机绝对路径，也不携带本机 `installation_id`。

## 发布与 readiness

发布方先在 `data_root/cloud-handoff-stage`（坚果云同步目录之外）创建完整目录：复制媒体、写两份 JSON、校验 schema、身份引用和 SHA-256、确认严格三文件；随后才将目录移动到最终日期目录。

同一卷使用目录 rename；跨卷时使用同步目录中的临时目录完成校验后再 rename。最终电话目录不会出现半包。坚果云网络传播可能逐文件发生，因此云端消费者也必须执行下列检查，而不是看到第一个文件就处理：

1. 目录内恰好三份普通文件；
2. 恰好一个 `audio.*`、`recording.json`、`event.json`；
3. 两份 JSON 分别通过 cloud package schema；
4. `recording_id` 一致；
5. `recording.json.media_filename` 与 `event.json.media_ref` 都指向当前 `audio.*`；
6. 实际媒体 SHA-256 同时等于 `recording.json.sha256` 和 `event.json.media_sha256`；
7. `event_id` 格式合法且稳定。

本机可用 `validate-cloud-package --package-dir <电话目录>` 独立执行同一验证。

## 销售身份与发布状态

旧三文件正式发布要求对应 event 已由 per-device effective-dated assignment 得到 `CONFIGURED` 销售身份；publisher 按每个 event 路由，因此同一台 PC 可同时发布多个销售。已有 legacy finalized event 继续可发布，但新未知设备不会继承 workstation-wide `config.local` 销售。UNASSIGNED call 仍可进入 call-fact 流，不会被错误塞进某个销售目录。

```powershell
.\.venv\Scripts\python.exe -m sales_mobile_ingest list-devices --discover
.\.venv\Scripts\python.exe -m sales_mobile_ingest assign-device --device-id "<dev_...>" --salesperson-id "S007" --salesperson-name "张三" --effective-from "2026-01-01T00:00:00+08:00"
.\.venv\Scripts\python.exe -m sales_mobile_ingest configure-cloud-handoff --sync-root "<用户确认的坚果云同步根>"
```

`--sync-root` 仅在操作者明确选择已有同步根时创建其下的 `销售通话数据` 专用子目录；程序永不从多个候选中自行选择。已有专用目录也可使用 `--root` 直接配置。

缺少身份时，录音和 CallLog ingest 继续运行，但发布状态为 `SALESPERSON_IDENTITY_UNCONFIGURED`，不创建错误销售目录。缺少 root 时为 `CLOUD_HANDOFF_ROOT_UNCONFIGURED`。两种情况都会在本机 state 记录未发布状态，等待后续补发。

## 幂等、冲突与后到 enrich

- `event_id` 是发布主键。已存在且通过完整验证、并且 `event_id`、`recording_id`、媒体 SHA-256 相同的目录计为 `already_published`，不复制第二份媒体。
- 已存在但包无效，或其稳定身份/媒体与当前 event 冲突，状态为 conflict，绝不静默覆盖。
- v1 已发布包是不可变快照。之后合法的号码、方向、销售显示名或时间 enrich 不会新建第二个电话目录，也不会覆写坚果云中的既有包；状态记录为 `published_immutable_enrichment_pending`，供未来版本设计显式修订/迁移流程。这避免云同步中途产生混合包。

## 云端消费者最小算法

```text
扫描 <cloud_handoff_root>/<salesperson>/<YYYY-MM-DD>/<call-folder>/
  -> 执行 readiness gate
  -> event.json: 销售身份、电话号码 -> CRM 用户/联系人 -> 0..N 项目候选
  -> audio.*: ASR
  -> 后续 Sales AI: 通话内容 + 候选上下文 -> 建议
```

电话号码不是 CRM 项目的唯一键；它只用于产生 0..N 个候选。本仓库不实现转写、CRM 匹配或云端消费者。

## 隐私与容量

不得把 `state`、`logs`、`diagnostics`、`inbox`、原始 `calls-*.xml`、probe 报告、本机配置、源码或 Git 数据放入 `cloud_handoff_root`。完整号码只可位于正式 `event.json`，不应出现在目录名、普通日志或文档。

v1 为正确性优先的媒体 copy，不自动删除本机 ready media，也不尝试 hard link。未来如需容量优化，必须先验证文件系统、坚果云读取语义、删除语义和 hash 不变性。
