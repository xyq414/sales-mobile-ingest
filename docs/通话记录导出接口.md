# 通话记录导出接口（验证中）

最后更新：2026-08-19。

## 当前状态

本文件定义的是公共 CallLog 文件导出的**实现边界和验收顺序**，不是已发布的 downstream contract。当前首个候选来源为用户在 OPPO 上主动使用 SyncTech `SMS Backup & Restore` 创建的 CallLog-only 本地 XML；Windows 在本次复核中连续 4 次未发现 MTP portable device（`WINDOWS_MTP_DEVICE_NOT_CURRENTLY_AVAILABLE`）。因此项目尚未读取该 XML，也没有确认 XML 根节点、属性名、属性类型、时间单位或方向枚举。

在取得这些真机证据前，`ready/events` 中现有 event 绝不被填入号码、联系人、方向或“确定通话时间”。

## 目标边界

```text
手机 CallLog
  -> 用户主动创建的公共导出文件
  -> Windows MTP 有界发现与只读复制
  -> 本机 staging / SHA-256 / 来源去重
  -> provider parser（以真实 schema 为准）
  -> canonical call row
  -> recording correlation
  -> 原子更新既有 communication event
```

`SMS Backup & Restore` 只是第一个 `VALIDATED_EXTERNAL_CALLLOG_EXPORTER` 候选；架构必须允许后来替换为另一种用户授权的公开导出器。下游仍只消费 `ready/events`，不需要知道 XML、MTP、手机品牌或 App 名称。

## 数据与隐私边界

- 原始 XML 只能保存在 gitignored 的 `data_root/diagnostics/calllog-backup`，并先落入临时 staging 后完成本机 SHA-256；它不是 `ready` 对象。
- 原始 XML、号码、联系人、完整源文件名和值不能进入 Git、contract example、README、普通日志或最终验收报告。
- state 只保存重复检测和处理恢复所必需的来源指纹、内容 hash、canonical ID 与处理状态；不得把诊断 XML 复制进仓库。
- 手机端与导出文件均只读：不删除、不移动、不改名、不回写，也不改变 SyncTech 设置。

## 真机 schema 出现后的最小 canonical row

实现时会将真实 exporter 字段映射为下列内部语义；任一源字段不可靠就保持 `null` / `unknown` 并记录 provenance，不能从文件名或显示时间猜测。

| 内部字段 | 含义 |
| --- | --- |
| `provider_id` / `provider_version` | 明确是哪一个已验证 exporter/parser。 |
| `source_artifact_sha256` | 本地完整复制的 XML 内容身份。 |
| `canonical_call_id` | 由 provider、已确认的稳定原始行身份字段和规范化语义组成的可复算 hash；用于跨 snapshot/late arrival 去重。 |
| `occurred_at` / `occurred_at_source` | 只在真实 XML 时间字段及单位被验证后写入。 |
| `duration_seconds` / `duration_source` | 只在真实 XML duration 语义被验证后写入。 |
| `phone_number_raw` / `phone_number_normalized` | 原始值保留在本机；规范化只在国家/格式证据充足时执行。 |
| `contact_name` | exporter 明确提供才使用；不由号码反查或猜测。 |
| `call_direction` | 只用经真实枚举验证的 exporter 值映射。 |

同一 XML 再次出现，或新的 full/archive/incremental 文件再次带有同一 canonical row，均不得产生第二个 event 或覆盖更可靠的既有证据。

## 关联与 event 提交规则

关联器只考虑时间距离、时长差与唯一候选数量。结果只能为 `EXACT`、`HIGH_CONFIDENCE`、`AMBIGUOUS` 或 `NO_MATCH`：

- `EXACT`：双方时间与时长证据都已验证且唯一，无冲突；
- `HIGH_CONFIDENCE`：唯一候选同时通过配置的时间、时长窗口，但至少一侧 provenance 不是实际通话发生时间；
- `AMBIGUOUS`：多个候选通过窗口，或身份字段冲突；
- `NO_MATCH`：没有通过窗口的候选。

当前录音的时间来源是 `wpd_modified_at`，不是已确认的通话发生时间；即使将来存在唯一 XML row，也不能仅凭它标为 `EXACT`。只有 `EXACT` 或 `HIGH_CONFIDENCE` 才允许用临时文件 + 原子替换更新既有 event；媒体、`recording_id`、`event_id` 和媒体 SHA-256 必须保持不变，JSON 最后出现仍是 commit signal。

## SyncTech 官方资料的可用结论

SyncTech 官方产品页说明该 App 可将 call logs 备份为 XML、先形成设备本地备份，并可设置 recurring scheduled time；这支持把它作为“用户主动导出 → MTP 文件读取”的候选，而不支持 Windows 直接读取 Android CallLog provider。[SMS Backup & Restore 产品页](https://www.synctech.com.au/sms-backup-restore/)

官方 FAQ 明确区分三种备份方式：默认的 full backup 每次包含当时全部 calls；archive mode 在同一初始文件追加新 calls；incremental backup 为后续新 calls 创建新文件，并可配置定期再建 full backup。因此实现必须以 artifact hash 与 canonical call ID 双层去重，不能按“每个 XML 是新数据”假设。[备份类型说明](https://www.synctech.com.au/faqs/backup-types/)

官方 FAQ 还说明：定时备份成功后会有通知；Android 13+ 可能需要允许 alarms/reminders，Android 11+ 可能自动撤销长期未用 App 的权限，部分厂商电量/后台限制会阻止任务。该 FAQ 给出了若干厂商示例，但没有提供 ColorOS/OPPO 的专项保证；因此 ColorOS 的实际后台可靠性仍是 `UNVERIFIED`，本轮没有改动手机上的任何设置。[定时备份 FAQ](https://www.synctech.com.au/sms-backup-restore/sms-faqs/)
