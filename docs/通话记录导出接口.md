# 通话记录导出接口

最后真实核验：OPPO 证据 2026-08-19；Call-first synthetic implementation 2026-08-30。

## 当前终态

首个 `VALIDATED_EXTERNAL_CALLLOG_EXPORTER` 已在 OPPO A6 Pro 5G 真机完成闭环：用户主动使用 SyncTech `SMS Backup & Restore` 创建 CallLog-only 本地 XML，Windows 通过普通 USB/MTP 只读发现、复制、解析并关联既有电话录音。

这不是 Android CallLog provider 经 MTP 直接暴露；这是**用户创建的公共导出文件**。SyncTech 只是第一个已验证 provider，不是项目的永久依赖。下游以 `ready/calls` 为电话事实主边界，以 `ready/call-links` 连接可选录音；`ready/events` 只保留旧 recording-backed compatibility。

## 已验证的真机证据

- MTP：发现 1 台 `OPPO A6 Pro 5G`、1 个指定导出目录、1 个 `calls-*.xml` 候选。
- 复制：XML 大小 656 bytes，经 staging、尺寸核验和 SHA-256 后保存为本机 gitignored artifact；第二次及后续运行均为 artifact duplicate。
- 实际 schema：根节点 `calls`；根属性 `backup_date`（integer）、`backup_set`（string）、`count`（integer）、`type`（string）；子节点 `call` 的字段包括 `date`、`duration`、`number`、`type`、`contact_name`、`presentation`、`readable_date`、`post_dial_digits`、`subscription_component_name`、`subscription_id`。常规输出仅含名称与类型，不含字段值。
- parser：已将真实 `date` 作为 epoch milliseconds、`duration` 作为非负秒数、`type` 作为整数；无法符合该 schema 的 XML 不会写入 canonical row。
- 关联：1 条 canonical row 与当前 190.028 秒录音唯一匹配；时长差 0.028 秒。WPD modified time 不是确定通话发生时间，直接比较不通过；采用明确记录的“Windows 本地 UTC 偏移 + 录音结束时间”对齐后，起始时间差 3.208 秒，结果为 `HIGH_CONFIDENCE`，不是 `EXACT`。
- event：仅在该唯一高置信关联后原子 enrich。`event_id`、`recording_id`、媒体路径及媒体 SHA-256 均保持不变；`phone_number_source=calllog_export`、`phone_number_confidence=medium`、`call_direction_source=calllog_export`。当前真实 XML 没有提供可用联系人值，因此 `contact_name` 仍为 `null` / `unknown`；`occurred_at_source` 与 `duration_source` 仍保留 WPD provenance。

## 生产流程

```text
Android CallLog
  -> 用户主动创建的公共 XML export
  -> Windows MTP 有界发现（指定目录 + calls-*.xml）
  -> diagnostics staging / size / SHA-256
  -> provider parser（真实 schema）
  -> canonical provider row
  -> phone-call/v1（无录音也发布）
  -> call-recording-link/v1 保守关联
  -> 仅 EXACT / HIGH_CONFIDENCE 时兼容 enrich 旧 event
```

`ingest --once` 和后台 `watch` 都会运行这一可选 enrichment 分支。公共 XML 不可用或解析失败时，录音采集仍会继续；不会因 CallLog 失败阻塞 `ready/recordings`。

## 去重、恢复与隐私

- XML artifact 用 SHA-256 去重；源路径/尺寸/modified time 仅用于避免不必要的复制。
- provider row ID 由 provider、经确认的 `date`、`duration`、`type`、原始号码及可靠 `subscription_id` 计算；联系人和 snapshot metadata 不参与。最终 `call_id` 再加入本机 enrollment `device_id`，因此 full/archive/incremental 不重复、双卡有明确维度、不同手机不合并。
- 未匹配 PhoneCall 和 RecordingAsset 都保留。每个 recording 有稳定 link identity，NO_MATCH/AMBIGUOUS 可在后续 reconciliation 更新为 EXACT/HIGH_CONFIDENCE；歧义时不会硬选。
- 原始 XML、provider row state 和关联诊断只保存在 `data_root/diagnostics/calllog-backup` 或 `data_root/state`。正式 PhoneCall/Link 在 gitignored data root 的 ready 目录；示例只使用显式 synthetic 值。
- 手机端及 XML 均只读：不删除、不移动、不改名、不回写，不改变 SyncTech 设置。

## SyncTech 官方资料与定时建议

SyncTech 官方说明该 App 可将 call logs 备份为 XML、先生成本地设备备份并支持 recurring schedule；这支持本项目的“用户导出 → MTP 读取”边界，但不代表 Windows 可直接访问 Android CallLog provider。[产品页](https://www.synctech.com.au/sms-backup-restore/)

官方 FAQ 说明默认 full backup 每次包含当时全部 call logs；archive mode 追加到既有文件；incremental mode 为新 call logs 新建文件。上述三种模式都要求 artifact hash 和 canonical row 双层去重。[备份类型说明](https://www.synctech.com.au/faqs/backup-types/)

官方 FAQ 还指出 Android 13+ alarms/reminders、Android 长期未用 App 的权限撤销及厂商后台限制可能影响计划任务；没有 OPPO/ColorOS 的专项保证。因此本项目目前只验证了手动创建的真机 XML，不把定时手机备份标为已验证。手机端设置没有被本项目修改。[定时备份 FAQ](https://www.synctech.com.au/sms-backup-restore/sms-faqs/)

## Snapshot freshness 与 call type

根 `backup_date` 只有在合法 epoch milliseconds 时才作为 backup timestamp；相对 import time 默认 48 小时以内为 FRESH，超过为 STALE，缺失/无效为 UNKNOWN。root `count`、`type/backup_type/mode` 只按真实属性保留。STALE/UNKNOWN 不阻止历史导入，但绝不表示“截至现在完整”；malformed export 不产生 PhoneCall，并保留私有 failure evidence。

Android/SyncTech raw type 1/2 映射 incoming/outgoing，3/5/6/7 分别保留 missed/rejected/blocked/answered externally disposition，4 为 voicemail disposition；未知值 raw-preserved + unknown。direction 与 disposition 分离，duration 不用于猜接听业务状态。`subscription_id`、`subscription_component_name` 和明确 slot 字段按原样保留；不会从 subscription string 推断 slot。
