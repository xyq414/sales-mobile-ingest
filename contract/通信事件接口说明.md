# communication event contract v1 接口说明

## 消费边界与提交信号

下游消费 `data_root/ready/events/<event_id>.json`。事件 JSON 是第二层 commit signal：它出现前，引用的 `media_ref` 和该媒体对应的 `ready/recordings/*.json` 必须已经存在、完成校验且 SHA-256 一致。事件路径和 `media_ref` 均相对于 `data_root`，不含 Windows 盘符、手机根目录或 MTP 实现细节。

首批只实现 `source_type=phone_call`。schema 使用字符串而非封闭枚举，为后续合规新增的通信来源保留扩展空间；新增来源不会改变电话事件的字段语义。

## 身份、时间与不确定性

- `event_id` 是 `SHA-256("communication-event/v1|phone_call|recording_id")` 加 `evt_` 前缀，可复算，重复发布同一录音不会产生第二个事件。
- `installation_id` 为本机 state 中首次生成的随机 UUID；它不是手机序列号、Windows 用户名或 Git 用户名，并且不进入仓库。
- `salesperson_id` 只能由 gitignored 的 `config.local.json` 明确配置。未配置时它为 `null` 且 `salesperson_identity_status=UNCONFIGURED`，程序不会猜测销售身份。
- `occurred_at_source` 明确区分 `filename`、`wpd_modified_at`、`wpd_created_at`、`import_time`、`calllog_export`、`unknown`；`occurred_at_confidence` 与证据强度对应。现有 OPPO 真机录音保留 `wpd_modified_at`，不会被 XML 的关联结果改写成确定的通话发生时间。
- 号码、联系人、方向、时长均携带来源/置信度。`unknown` 和 `null` 是正确值，不是待填的猜测。`calllog_export` 只会在已验证 exporter 的 canonical row 与该录音形成 `EXACT` 或 `HIGH_CONFIDENCE` 的唯一关联后出现；本机当前真机样本为 `HIGH_CONFIDENCE`，故号码置信度为 `medium`。号码规范化仅移除空白、括号、短横线等外观分隔符，保留 `+`，不会补 `+86` 或从文件名臆测号码。

## 下游语义：给 Sales AI 的稳定输入

`phone_event` 只是一次已验证的电话通信事实，不能直接等同于某个 CRM 项目。建议下游依次执行：

```text
phone_event
  -> phone_number_normalized（若存在）
  -> CRM 用户 / 联系人候选
  -> 0..N 个候选项目或委托
  -> 转写
  -> 内容推断与人工/业务规则确认
```

关键约束：**电话号码绝不能直接映射为唯一项目。** 一个号码可能没有联系人、多个联系人、多个历史项目，或者一个电话根本不对应项目。本仓库只提供可靠的事件、媒体引用和 provenance；不实现 CRM、转写、匹配或推断。

## 字段摘要

| 字段组 | 含义 |
| --- | --- |
| 身份 | `event_id`、`recording_id`、`installation_id` 负责可复算对象关联与本机隔离。 |
| 时间 | `occurred_at` 加来源与置信度，避免低质量时间被当作通话事实。 |
| 人员与号码 | `salesperson_id`、号码、联系人均允许 `null`/`unknown`，且来源单独表达。 |
| 媒体 | `media_ref` 是相对引用，`media_sha256` 与 ready 媒体字节一致。 |
| 适配 | `adapter` 与 `adapter_evidence_status` 仅报告采集证据级别；`OFFICIAL_DOC_CANDIDATE` 不等于真机支持。 |

合成样例见 [examples/communication_event.phone_call.example.json](examples/communication_event.phone_call.example.json)，机器校验规则见 [communication_event.schema.json](communication_event.schema.json)。
